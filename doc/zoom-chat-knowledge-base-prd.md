# Zoom Chat 知识库工具 PRD

> 文档版本：v0.2  
> 更新日期：2026-10-01  
> 暂定产品名：Zoom Chat Knowledge Hub

> **v0.2 产品决定**：知识库改为自动沉淀，不再要求人工批准或手动 `Add to KB`。历史消息一次性直接建库；近期 Topic 静默达到阈值后自动归档。若本文旧章节与第 16 节冲突，以第 16 节为准。

## 1. 产品概述

Zoom Chat Knowledge Hub 是一个基于 Zoom Team Chat API 的只读采集、归一化和检索工具。它按需读取用户有权访问的频道新消息，将销售、产品和支持讨论整理为可追溯的问题、需求、答复、决策与行动项，并为重复问题推荐已有答案。

产品默认不实时监听、不自动发消息。用户点击“同步”或运行同步任务时，系统读取上次成功同步之后的新内容，并结合既有知识生成增量摘要。

## 2. 已验证的技术事实

- 当前 OAuth 应用可以列出授权用户有权访问的频道；测试账号共返回 161 个会话/频道。
- 已验证 `GET /chat/users/me/channels`、`GET /chat/users/me/messages` 和线程读取所需的三个只读权限。
- `[INT] - CS <> Product` 可通过 API 返回明文正文，能够进行问题归纳和摘要。
- `[EXTERNAL] Zoom&DTEN Win ZR项目交流群` 的客户端能显示正文，但 API 只返回 `[This is an encrypted message]`；API 仍可返回发送者、时间、线程关系、附件名称和 reactions。
- Zoom 消息查询时间必须输出到整秒；带微秒的 RFC 3339 时间在实测中可能静默返回空结果。
- Zoom 消息接口只提供最近六个月范围内的历史查询，因此知识库需要持续增量保存，不能依赖随时重新全量回溯。

官方接口参考：[Zoom Chat API](https://developers.zoom.us/docs/api/chat/)、[Zoom OAuth](https://developers.zoom.us/docs/integrations/oauth/)。

## 3. 目标与非目标

### 3.1 产品目标

1. 列出全部可见频道，并标识正文可读性。
2. 增量采集新消息和线程回复，保留上下文与原始来源。
3. 将讨论抽取为问题、需求、答复、决策、行动项和状态更新。
4. 识别语义重复问题，形成“标准问题 + 推荐答案 + 证据”的知识条目。
5. 提供可搜索、可筛选、可审核的 Web UI。
6. 提供 `@我` 收件箱，突出直接提问、待回复和已解决事项。
7. 所有 AI 结论必须能回溯到 Zoom 原消息，不允许无来源回答。

### 3.2 MVP 非目标

- 不自动向 Zoom Chat 发送回复。
- 不绕过或破解 Zoom 消息加密。
- 不下载和解析附件正文；MVP 仅保存附件元数据。
- 不采集授权用户无权访问的频道或其他用户的私有数据。
- 不把附件名、表情或活跃度推断成确定的消息正文。

## 4. 用户与核心场景

### 4.1 用户角色

- **知识库管理员**：配置 OAuth、选择频道、管理保留策略和审核规则。
- **产品/支持负责人**：查看问题聚类、维护标准答案、跟踪未解决问题。
- **销售人员**：搜索相似问题、获取带来源的推荐答案。
- **普通授权用户**：查看与自己相关的 `@我` 消息和待办。

### 4.2 核心使用流程

1. 用户完成 Zoom OAuth 授权。
2. 系统列出频道并执行正文可读性探测。
3. 用户勾选需要纳入知识库的频道和首次回溯范围。
4. 用户点击“同步”；系统仅拉取上次游标之后的新消息。
5. 系统按线程聚合上下文，抽取问题、答复、决策和行动项。
6. 系统把新问题与历史知识条目进行相似度匹配。
7. 高置信度重复问题展示推荐答案；低置信度内容进入人工审核队列。
8. 用户通过搜索或 `@我` 收件箱进入详情页，查看摘要、原始证据和 Zoom 来源链接。

## 5. 功能需求

### FR-1：OAuth 与身份

- 使用 User-managed OAuth + PKCE，MVP 不使用客户端密钥。
- OAuth token 必须保存到操作系统凭据库或加密密钥库，不得继续使用明文 JSON。
- 记录当前用户的 Zoom user ID、member ID 和邮箱，用于识别 `at_items` 中的直接 `@我`。
- 若获取当前身份需要新增权限，只增加 `GET /users/me` 对应的最小资料读取 scope；实施时以 Zoom Marketplace 实际显示的 granular scope 为准。
- 支持刷新令牌、重新授权和撤销授权后的数据清理。

### FR-2：频道目录与可读性探测

频道列表显示：

| 字段 | 说明 |
|---|---|
| 频道名称 | Zoom 返回的频道名 |
| 类型 | 频道、群聊、1:1、共享空间等 |
| 内部/外部 | 能从类型或频道信息确认时显示；无法确认时显示未知 |
| 正文状态 | 可读、加密、混合、待判定、无权限、接口错误 |
| 最近消息时间 | 最近一次成功读取到的消息时间 |
| 已收录数 | 本地保存的消息和知识条目数量 |
| 同步状态 | 未选择、待同步、同步中、成功、失败 |

正文状态判定规则：

1. 在用户配置的探测窗口内抽样最多 20 条消息。
2. 至少一条包含非空且非占位符正文，标记为 **可读**。
3. 出现 `[This is an encrypted message]` 或明确加密元数据，且没有任何明文，标记为 **加密**。
4. 同一频道同时出现明文与加密占位符，标记为 **混合**。
5. 抽样窗口内没有消息，标记为 **待判定**，不得误标为加密。
6. API 返回 403/404 时分别标记 **无权限/频道失效**。

加密频道仅保存允许获取的元数据，并在 UI 显示明确限制：“Zoom 客户端可解密，但 API 未提供正文”。

### FR-3：增量同步

- 首次同步默认回溯 30 天，管理员可选 7、30、90 或最多约 180 天。
- 每个频道保存独立游标：`last_success_timestamp`、最近消息 ID 集合和最近线程更新时间。
- 后续同步从上次成功时间向前重叠 5 分钟读取，以覆盖延迟到达或编辑消息。
- 以 `channel_id + message_id` 做幂等去重。
- 时间统一保存为 UTC，UI 按用户时区显示；请求时间精确到秒，不输出微秒。
- 支持分页、限速退避、失败重试和断点续传。
- 线程主消息与回复作为一个“讨论单元”处理；仅对新增或有更新的线程重新分析。
- 默认不改变 Zoom 消息的已读/未读状态。
- 同步日志记录频道、时间范围、读取数、新增数、更新数、加密数、失败原因与耗时。

### FR-4：内容抽取与分类

每个讨论单元可产生零到多个结构化记录：

- **问题**：用户询问、故障、澄清请求。
- **需求**：产品能力、客户需求、交付或集成请求。
- **答复**：解释、解决方案、规避方法、文档链接。
- **决策**：明确确认的方案、结论或优先级。
- **行动项**：负责人、动作、截止时间、状态。
- **状态更新**：测试结果、已修复、等待客户、无法复现等。

每条结构化记录必须包含：

- 标题与规范化描述。
- 产品、模块、客户、地区、严重程度、标签。
- 状态：未解决、部分回答、已解决、过期、待审核。
- 置信度。
- 来源频道、线程、消息 ID、发送者和时间。
- 证据片段；加密消息不得生成伪造片段。

### FR-5：重复问题归一化

采用“关键词检索 + 向量检索 + 结构化字段”的混合匹配：

1. 清洗问候、签名、纯 `@人` 和无意义短句。
2. 抽取产品、型号、平台、症状、错误码、客户环境和期望行为。
3. 生成规范化问题，例如：  
   `D7X AI Board + Zoom Rooms + 外接功放/天花板扬声器 + 回声或输出路径异常`。
4. 与历史问题计算语义相似度，并校验产品/型号等硬条件。
5. 高置信度聚入已有知识条目；中等置信度进入“可能重复”审核队列；低置信度创建新候选条目。
6. 一个标准问题可关联多个原始提问和多个答案，但只能有一个当前“推荐答案”。
7. 推荐答案必须显示来源数量、最后验证时间、适用范围和冲突信息。

### FR-6：回答推荐

- 搜索或新问题详情页显示最多 5 个相似问题。
- 推荐答案必须附来源消息和知识条目链接。
- 当来源互相冲突、过期或置信度不足时，明确显示“不建议直接回答”。
- MVP 仅支持复制建议答案；不申请 Zoom 写权限。
- 后续版本可增加“人工确认后发送”。自动发送必须单独增加写 scope、审计日志、频道白名单和熔断机制。

### FR-7：`@我` 收件箱

- 解析消息 `at_items`，用当前用户的 user ID/member ID 识别直接 `@我`。
- 区分：直接 `@我`、`@所有人`、回复我的消息、仅在同一线程中出现。
- 展示消息上下文、频道、发送者、本地时间、线程摘要和来源链接。
- 状态：未处理、已查看、已回复、无需处理、稍后处理。
- MVP 状态仅保存在本地系统，不调用 Zoom 的“标记已读”接口。
- 对只有 `@我` 而没有问题正文的消息，应加载同一线程前文再生成任务描述。

### FR-8：搜索与知识库 UI

#### 页面 A：总览

- 上次同步时间、读取频道数、新消息数、加密消息数。
- 新问题、未解决问题、重复问题、待审核答案和 `@我` 数量。

#### 页面 B：频道目录

- 全量频道表、可读状态、探测原因、最近同步和收录开关。
- 支持按“可读/加密/待判定/外部”筛选。

#### 页面 C：`@我` 收件箱

- 按时间、频道、处理状态和紧急程度筛选。
- 详情中展示线程上下文与建议答复。

#### 页面 D：知识搜索

- 自然语言搜索和字段筛选。
- 结果显示标准问题、推荐答案、置信度、适用范围、最后验证时间和来源数。

#### 页面 E：问题详情

- 标准问题、相似原始提问、答案历史、冲突答案、决策、行动项和时间线。
- 支持合并、拆分、编辑、批准、废弃和重新分析。

#### 页面 F：同步与设置

- OAuth 状态、频道选择、回溯窗口、时区、保留周期、模型设置和同步日志。

## 6. 信息架构与数据模型

核心实体：

| 实体 | 关键字段 |
|---|---|
| `users` | Zoom user ID、member ID、email、timezone |
| `channels` | channel ID、name、type、readability status、selected |
| `sync_cursors` | channel ID、last success timestamp、last run status |
| `messages` | message ID、channel ID、thread root ID、sender、timestamp、正文/加密占位、mentions |
| `attachments` | file ID、文件名、大小、类型；不长期保存临时下载 JWT |
| `discussion_units` | 线程根、摘要、参与者、开始/结束时间 |
| `knowledge_items` | 标准问题、推荐答案、分类、状态、置信度、版本 |
| `knowledge_sources` | knowledge item 与原始消息/线程的多对多关系 |
| `mentions` | message ID、mention type、target user、处理状态 |
| `review_tasks` | 重复候选、答案冲突、低置信度抽取、审核人 |
| `sync_runs` | 请求范围、数量统计、错误与耗时 |

## 7. 推荐技术架构

```mermaid
flowchart LR
    Z[Zoom Team Chat API] --> I[增量同步 Worker]
    I --> R[(原始消息库)]
    R --> P[线程聚合与内容抽取]
    P --> K[(知识条目库)]
    K --> V[(向量索引 + 全文索引)]
    R --> M[@我识别]
    V --> A[检索与推荐服务]
    M --> U[Web UI]
    A --> U
    U --> H[人工审核与知识维护]
    H --> K
```

### 7.1 MVP 技术栈

- 后端：Python + FastAPI。
- 同步任务：进程内任务队列或 APScheduler；按需运行优先。
- 数据库：SQLite（单用户本地 MVP），启用 FTS5 全文检索。
- 向量检索：本地向量库或 SQLite 向量扩展。
- UI：React/Next.js，或先用轻量管理 UI 验证流程。
- 密钥：Windows Credential Manager/DPAPI；不得写入仓库或日志。

### 7.2 团队版升级

- PostgreSQL + pgvector。
- 独立 Worker 与 Redis 队列。
- SSO、RBAC、审计日志、集中密钥管理和备份。
- 按用户隔离 OAuth token 与可见数据，避免一个用户看到另一个用户无权访问的来源。

## 8. AI 处理策略

- 先做确定性线程聚合和规则分类，再调用模型抽取。
- 模型输入只包含当前授权范围内的正文和必要上下文。
- 保存模型版本、提示模板版本、输入消息 ID 和输出置信度。
- 回答采用检索增强生成；没有可靠来源时返回“知识库中暂无可信答案”。
- 加密消息只参与活跃度统计，不送入语义模型。
- 默认不把公司聊天发送到公共第三方模型；部署前必须确定批准的模型和数据处理区域。

## 9. 安全、隐私与合规

- 最小权限：MVP 保持聊天只读；单独评审任何写权限。
- Token 加密保存，日志必须过滤 access token、refresh token 和附件下载 JWT。
- 数据库加密、备份加密、访问审计和管理员操作审计。
- 对外部频道设置独立白名单和更短保留周期。
- 支持按频道停止采集、按来源删除、撤销授权后清理相关数据。
- 附件下载 URL 通常包含短期凭证，不应长期入库；只保存 file ID、文件名、大小和来源消息 ID。
- 对姓名、邮箱、客户名等字段提供脱敏或权限控制。
- 明确知识条目“内部可见范围”，避免把外部客户内容传播给无关人员。

## 10. MVP 范围与迭代计划

### 阶段 0：技术验证（已基本完成）

- OAuth + PKCE。
- 列出频道。
- 读取明文消息与加密占位符。
- 验证线程、mentions、附件元数据和时间查询。

### 阶段 1：采集与可见性（约 1–2 个工程周）

- 频道目录与可读性五态/六态识别。
- 频道选择、首次回溯和增量游标。
- 原始消息、线程、附件元数据和同步日志入库。
- `@我` 基础收件箱。

### 阶段 2：知识抽取与搜索（约 2–3 个工程周）

- 问题/需求/答复/决策/行动项抽取。
- 混合检索、相似问题聚类和知识详情页。
- 人工审核、合并、拆分和推荐答案维护。

### 阶段 3：答案推荐与运营（约 1–2 个工程周）

- 新问题自动匹配已有答案。
- `@我` 建议回复、知识新鲜度和冲突提醒。
- 指标看板与数据质量报告。

### 阶段 4：可选自动化

- 经安全评审后增加“人工确认后发送”。
- 后续再评估实时事件订阅、自动回复和团队级多用户部署。

## 11. 验收标准

1. 能分页列出授权用户的全部频道，结果与 Zoom API 数量一致。
2. 可读频道、加密频道、无近期消息频道不会相互误判。
3. 第二次同步只新增新消息；重复运行不会产生重复记录。
4. 编辑消息、延迟消息和线程回复能通过重叠窗口更新。
5. 直接 `@我` 识别准确率在人工抽样中达到 95% 以上。
6. 每个 AI 生成的摘要和答案都至少关联一个原始来源；无来源内容不能发布为推荐答案。
7. 相似问题候选 Top 5 的人工可接受命中率达到 80% 以上后，才开放自动归并建议。
8. 加密消息不会被模型推测为正文，也不会生成确定性答案。
9. 日志、数据库和 UI 不显示 OAuth token 或附件下载 JWT。
10. 撤销 OAuth 后不能继续同步，且管理员可以删除已采集数据。

## 12. 成功指标

- 重复问题被已有知识命中的比例。
- 销售找到可用答案的中位时间。
- 推荐答案的人工采纳率。
- 未解决问题平均停留时间。
- `@我` 消息漏检率和平均响应时间。
- 有来源知识条目占比、过期知识占比、答案冲突数。
- 每次同步成功率和 API 错误率。

## 13. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 加密频道无正文 | 无法构建语义知识 | 显示限制；仅收元数据；优先选择明文频道 |
| 六个月历史窗口 | 无法晚期完整回溯 | 尽早持续同步并本地保留合规副本 |
| 重复问题误归并 | 错误答案传播 | 硬条件校验、置信度阈值、人工审核 |
| 旧答案继续推荐 | 销售获得过期信息 | 知识有效期、最后验证时间、冲突提醒 |
| 敏感信息扩散 | 合规和客户风险 | RBAC、脱敏、频道白名单、来源权限继承 |
| API 限速或失败 | 同步不完整 | 分页、退避、断点续传、同步日志 |
| 模型幻觉 | 产生无依据回答 | 强制来源引用；无可信来源则拒答 |

## 14. 待确认的产品决策

1. 首批纳入哪些频道：建议先选 5–10 个明文、高价值销售/产品频道。
2. 本地单用户工具还是公司内部多人 Web 服务。
3. 允许使用哪一种 AI 模型，聊天正文能否离开公司网络。
4. 原始消息和知识条目的保留期限。
5. 谁拥有标准答案的批准权，按产品线还是统一管理员。
6. 是否需要纳入 1:1 私聊；建议 MVP 默认排除。
7. 是否允许外部频道进入知识库；建议默认关闭、逐个批准。
8. `@我` 是否只展示直接 mention，还是同时纳入回复我的消息和 `@all`。

## 15. 建议的 MVP 默认配置

- 只读 OAuth。
- 仅采集人工勾选的群组频道；默认排除 1:1 私聊、会议临时会话和个人会议室。
- 首次回溯 30 天，每次手动同步；稳定后可改为每小时或每天。
- 外部频道默认不采集；加密频道只保留元数据。
- 推荐答案必须人工批准；不自动发送。
- 原始消息保存 180 天，知识条目长期保存但保留来源和版本。
- 本地 MVP 使用 SQLite + OS 凭据库；多人版再迁移 PostgreSQL。

## 16. v0.2：自动知识沉淀与跨语言查询（已确认）

### 16.1 产品原则

- `Conversation Topics` 是近期、仍可能变化的交流区，不是知识发布审批队列。
- `Knowledge Base` 是历史交流的自动归档和查询层，不需要人工逐条加入。
- 知识内容按原始对话语言保存，不生成永久中英翻译副本。
- 翻译和跨语言扩展只发生在查询阶段，不改写库存内容。
- 所有摘要、结论和搜索结果必须能回溯到原始 Zoom Chat 消息。

### 16.2 首次历史初始化

首次建立知识库时，对已选择频道、本地已同步的历史消息执行一次性扫描：

1. 以当前时间减去成熟阈值作为分界线；默认阈值为 14 天。
2. 最后活动早于分界线的完整话题直接进入 Knowledge Base，不在 Conversation Topics 中展示。
3. 最近 14 天仍有活动的话题进入 Conversation Topics。
4. 一个话题即使开始于 14 天前，只要最近 14 天有回复，整个话题都留在 Conversation Topics，不允许拆分归档。
5. 历史任务必须批处理、可恢复、有 checkpoint，并对相同输入保持幂等。
6. 进度状态显示：已扫描消息、识别话题、创建知识、合并知识、跳过数量、失败数量和已用时间。
7. 已被 `Do not track` 覆盖的来源、加密占位消息和未选择频道不进入知识库。

### 16.3 日常自动归档

每次 `Sync Selected Channels` 成功后，系统自动运行成熟度扫描：

```text
New Zoom messages
  → Conversation Topics
  → inactive for 14 days
  → final AI summarization in source language
  → create/update Knowledge Base
```

- 成熟度以 Topic 的最后一条消息时间计算，而不是创建时间。
- 默认 14 天；Settings 可提供 7、14、30 天，默认 14 天。
- 无明确结果的话题仍可入库，状态保存为 `Unresolved`、`Waiting` 或 `Partially resolved`。
- 已归档知识后来出现新消息时，旧版本保持可查询，并标记 `New activity detected`；新交流再次静默后生成知识新版本。
- 从 14 天改为更短阈值时，下次扫描归档新符合条件的 Topic；改为更长阈值不删除既有知识。

### 16.4 Conversation Topics 页面

Topic 卡片保留：标题、问题、讨论、当前结果、状态、最后活动时间、来源消息、置信度和群组。

操作仅包括：

- `Search KB`：使用当前 Topic 的标题、问题摘要、标签、产品、客户和原始语言查询已有知识，并在卡片下方显示相似结果。
- `Do not track`：隐藏该具体话题/线程及其后续高度重叠版本，并永久排除自动归档；不作为全局语义黑名单。
- `View Original Messages`：展开逐字保存的 Zoom Chat 证据。

删除 `Add to KB`、人工 review status 和手动批准流程。`Search KB` 不改变 Topic 或知识状态。

查询结果显示：相似度、原始标题、来源语言、状态、问题摘要、结论摘要、最后更新时间及 `View Knowledge`。无命中时显示该 Topic 将在达到静默阈值后自动归档。

### 16.5 原始语言存储

- 英文对话生成英文知识标题、问题摘要和结果摘要。
- 中文对话生成中文知识标题、问题摘要和结果摘要。
- 以最初问题/线程根的语言作为主要 `source_language`；混合对话中的原文、专有名词和引用保持原样。
- AI 可以总结，但不得为了统一展示语言而翻译库存内容。
- 原始 Zoom 消息逐字保存并单独关联，不被摘要覆盖。
- 知识条目至少保存 `source_language`、原始语言标题、问题、背景、结果、状态、标签、首次/最后交流时间和来源引用。

不同语言但语义相同的条目默认保持独立原始语言记录，可通过 `Related knowledge` 关联；不得通过翻译后覆盖其中一条来强行合并。

### 16.6 跨语言知识查询

查询采用混合召回：

1. 使用用户原始查询做关键词和字段检索。
2. 检测查询语言，并临时生成另一种语言的查询变体。
3. 使用多语言 embedding 做语义相似度检索。
4. 对产品、型号、客户、错误码和功能名做精确条件校验。
5. 合并、去重并排序原始查询、翻译查询和向量查询结果。

翻译后的查询只用于召回，不写入 Knowledge Base。结果默认展示库存的原始语言；可提供 `Translate for viewing`，但临时译文不保存为事实来源。

### 16.7 Knowledge Base 默认页面

无搜索词时展示：

- `Recently added knowledge`
- `Recently updated knowledge`
- `Unresolved knowledge`
- `Knowledge with new activity`

每项显示原始标题、来源语言、解决状态、关联交流次数、原始消息数量、最后交流时间和知识更新时间。详情页显示完整摘要、版本历史、关联话题及原始消息时间线。

### 16.8 验收标准

1. 历史消息可一次性建库且不出现在 Conversation Topics。
2. 历史任务中断后可继续，重复运行不重复创建知识。
3. 最近 Topic 在达到静默阈值前不自动入库。
4. `Do not track` Topic 及其同线程/高度重叠版本永不入库。
5. 达到阈值后无需人工操作即可自动创建或更新知识。
6. 英文来源保存英文知识，中文来源保存中文知识。
7. 中文查询可以命中英文知识，英文查询可以命中中文知识。
8. 查询翻译不修改库存字段，结果仍可回溯原始 Zoom 消息。
9. Conversation Topics 不出现 `Add to KB`，只提供 `Search KB`、`Do not track` 和来源查看。
